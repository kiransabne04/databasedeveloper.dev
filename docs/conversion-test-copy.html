Get the scriptBook a 15-minute call

1. Download the script

Download walstack-snapshot.sql

2. Run it during a busy period

Use PostgreSQL 13 or newer on RDS, Aurora or a self-managed server. Use an account with pg_monitor, PostgreSQL's built-in monitoring role. On RDS or Aurora, an administrator can grant it with GRANT pg_monitor TO <user>;.

Open a terminal in the script's folder. Replace the host, user and database names with your own.

psql -X -h <host> -p 5432 -U <user> -d <database> \
     -f walstack-snapshot.sql -o walstack-snapshot-1.txt
Copy command

One run is fine. If you can, run it again about an hour later. Change the output filename to walstack-snapshot-2.txt.

Comparing two runs shows what's growing now. A single run gives totals since statistics were last reset.

The script usually takes a few seconds. Each statement has a 10-second timeout. If it waits on a lock for one second, the script continues to the next statement.

3. Check what you're sharing

What it reads

  • PostgreSQL's own statistics and catalog, including settings, expensive queries, table and index activity, and index definitions.
  • Foreign keys that may need a supporting index, blocked sessions, connections, cleanup activity and replication health.
  • Column names and types for the 10 largest tables. Set show_schema off to omit the column listing. Index and foreign key definitions can still contain column names.

What it leaves alone

  • It doesn't read rows from your application tables, write data, change persistent settings or create objects.
  • It doesn't run your queries or ask PostgreSQL to explain their execution plans.
  • PostgreSQL usually replaces query values with markers like $1 and $2. Sensitive text can still appear. Set show_query_text off to omit query text.

Read every file before sending. Delete anything you don't want to share, including sensitive names or details in screenshots.

How the three business days work

The clock starts when I have read-only access or the output of scripts you run. You keep control of production changes.

  1. Day 1. I match the symptom to a time window. I compare query timings with traffic, database activity and recent releases.
  2. Day 2. I check which explanations fit. If two causes look alike, I ask for the smallest extra check that could distinguish them.
  3. Day 3. I send the report with the proposed SQL, risks, rollback steps and before-and-after checks. You get a 45-minute review call.

At the 14-day follow-up, I compare results with the original symptom and explain what changed.

What can the data prove?

Two captures can show that one query accounted for most of the extra database time. A single total can't tell me when the increase began.

If history is missing or the problem didn't recur, I say so. I explain which next measurement would settle the question.

Upgrade readiness · /postgresql-upgrade-readiness

PostgreSQL Upgrade Readiness

Get off PostgreSQL 14 before Extended Support adds to your bill.

RDS standard support ends on 28 February 2027. From 1 March, keeping an enrolled database on 14 adds an hourly charge.

For provisioned instances, AWS charges per virtual CPU-hour. The rate depends on the region and support year. Count each billable standby and replica. If you disabled Extended Support, AWS can upgrade the database instead.

For example, at a regional rate of $0.10 per virtual CPU-hour, four virtual CPUs running for 720 hours add $288. Check your region for the actual rate.

What I check

I check which target version your application can use and which add-ons need attention. I look at the busiest queries before the move so your engineers know what to compare afterwards.

  • Database and extension versions, application drivers and how the application opens connections.
  • Large tables, replicas and any systems that copy changes from the database.
  • Queries your customers depend on, their response times and how PostgreSQL runs them today.

What you get

A written list of blockers, the upgrade path I recommend and checks to rehearse on a test copy. I name the timings and errors to watch after the switch.

You get clear conditions for proceeding, stopping or rolling back. The rollback plan covers what happens to writes accepted after the switch. Your team owns the production change.

See a sample upgrade report. I built it on a demo database.

Technical details for your engineer

On self-managed PostgreSQL, pg_upgrade --check tests whether the old and new installations are compatible. It can't predict how quickly an important query will run.

On RDS or Aurora, I check whether a blue/green deployment fits. That means testing the new version on a separate environment before switching traffic.

I check replication slots, the bookmarks other systems use to resume copying changes. I document how to restart those systems and check for missing changes.
